数据需求说明 · 0G Chain 指标模块

Partner 合约清单要求

Solutions Hub 的「0G Chain」模块要按 partner 展示链上交易、gas 消耗和 TVL。 这些指标全部依赖一份映射：哪个 partner 拥有哪些链上合约。 这份映射 0gscan 侧没有，需要业务侧提供。

需求方 Chain / 0gscan 后端 提供方 Solutions Hub / 业务侧 交付形式 CSV
背景

Router 侧是按请求头 X-0G-Source-Id 给用量打标的，它记录的是「哪个 partner 发起了请求」， 但完全不知道这个 partner 在链上部署了什么合约。 而链上指标只能靠合约地址来归属。这中间缺的一环，只能由你们补上。

我们沿用同一个 source_id 作为 partner 身份，这样同一个 partner 在 PC、Storage、Pay、Chain 四个模块里是同一个身份，数字可以横向对比。

必填字段

需要提供什么

字段必填说明
source_id 必填 必须与 Router 侧 X-0G-Source-Id 的值完全一致，包括大小写。最长 64 字符。
partner_name 必填 展示名称，dashboard 上给人看的。最长 128 字符。
contract_address 必填 0x 开头的 40 位十六进制地址。一个 partner 可以有多行，每行一个地址。
effective_from 可选 留空即「自始生效」。只有合约转让或更换时才需要填。
effective_to 可选 留空表示仍然有效。合约下线后填写下线日期。
关键判断

该给哪些合约

最容易给错的地方

我们只统计用户交易直接打到的合约。 所以这份清单要的是「入口合约」，不是「我们部署过的所有合约」。

举个例子。假设某个 partner 部署了 1 个 Router 合约和 10 个 Pool 合约， 用户都是调用 Router，Router 再在内部调用 Pool：

应该提供
Router 合约

用户交易的目标地址是它，能统计到全部交易数和 gas 消耗。

给了也是零
10 个 Pool 合约

没有任何用户交易直接指向它们，交易数和 gas 都会是 0。

反过来，如果用户会直接调用多个入口（比如 Swap、Staking、NFT Mint 是三个独立合约）， 那三个都要提供，漏掉哪个哪部分数据就没有。

代理合约请提供 proxy 地址，不要提供 implementation 地址 —— 用户交易的目标是 proxy。

交易归因和 TVL 要的可能不是同一批合约

这一点需要特别留意，因为两类合约经常完全不重叠：

指标需要的合约
交易数 / gas / 活跃地址 用户直接调用的入口合约，比如 Router
TVL 实际持有资产的合约，比如 Vault、Pool、Treasury

入口 Router 通常不持币，持币的 Pool 通常没有直接交易。 请提供两类的并集。 某个合约只满足其中一类时，另一个指标显示 0 是正常的，不是数据错误。

排除项

不要提供的

  • EOA 钱包地址（部署者钱包、运营钱包）—— 归因是按交易的目标地址匹配的，钱包地址几乎不会作为目标，给了也是 0。
  • 测试网合约 —— 本模块只统计 0G 主网。
  • 已被其它 partner 认领的合约 —— 同一个合约在同一时间段内只能归属一个 partner，否则会重复计数。我们导入时会检查并拦截，需要你们先澄清归属。

待确认

需要你们答复的两个问题

一、source_id 的格式约束是什么？
Router 的 admin API 文档没有定义字符集和长度上限。我们目前按最长 64 字符建表。 如果实际可能更长，需要现在就调整表结构 —— 上线后再改代价大得多。
二、source_id 区分大小写吗？
如果 Router 侧对请求头的值做过归一化（比如统一转小写），我们这边必须跟着做， 否则同一个 partner 会被拆成两条互不相干的记录。
接口调用

凭证与调用方式

指标接口不是公开接口，每次调用都要带凭证。凭证由 0gscan 运维签发， 没有自助注册页面 —— 需要开工单向 0gscan ops 申请，线下交付。 

GET /open/partner/chain-metrics?source_id=acme-labs
Authorization: Bearer <key>

会签发两种凭证，按用途申请：

凭证能做什么给谁
partner:read 读取全部指标接口 dashboard 后端 / 同步任务
partner:write 额外可通过接口注册合约映射 需要自助维护注册表时才申请
必须由你们承担的一件事

凭证是服务级的，不是每个 partner 一个。 持有凭证即可读写所有 partner 的数据。

所以「哪个登录用户能看哪个 partner」这层判断，必须由 Solutions Hub 后端完成。 0gscan 不知道用户与 partner 的对应关系，不做这层校验。 切勿把凭证下发到浏览器或客户端 —— 请求要从你们的后端发出。

调用失败时的返回

状态码code含义
401invalid_auth未带凭证，或凭证无效/已过期
403insufficient_scope凭证有效但权限不足，例如用只读凭证调注册接口
400incomplete_date_range日期只给了一端，两端必须同时给或同时省略
400unknown_address:0x…该地址链上从未出现过
400address_owned_by_other_partner:0x…合约已归属其它 partner
 
{ "object": "error", "code": "insufficient_scope", "message": "..." }

两个数据处理上的坑

  • 金额字段必须用 BigInt 解析。 gas 和 TVL 数量都是整数字符串，单位是 neuron（1 0G = 1018）。 实际数值如 92027689956383148142 已远超 JavaScript Number 的安全范围， 直接 Number() 会静默丢精度。
  • 缺失的日期不等于 0。 时间序列里没有某天的行，表示那天该 partner 没有交易； TVL 历史的缺口表示那天没能采到快照，且事后无法补齐。 画图时补 0 会得到错误的曲线。
两条路径

清单也可以通过接口提交

前面描述的 CSV 是首批导入的方式，由 0gscan ops 代为写入。 如果你们希望自助维护注册表，可以申请写凭证后调接口： 

POST /open/partner/contracts
Authorization: Bearer <write-key>
Content-Type: application/json

{
  "source_id": "acme-labs",
  "name": "Acme Labs",
  "addresses": ["0x61bb71442749d13a4bb7257dfbfff0452ae937f9"]
}

重复提交同一地址不会报错。字段含义、该给哪些合约、以及各种校验失败的原因， 与前面 CSV 的要求完全一致。

接口提交的当前限制

通过接口注册不会自动补齐该合约的历史数据 —— 指标从注册后的次日开始产生。 需要历史数据的话，仍要请 0gscan ops 执行一次回填。

另外接口目前只能新增映射，不能下线。合约转让或停用需要联系 ops 处理。

首批清单交付后才能开始导入和回填，是整个模块上线路径上的阻塞项。
接口凭证请向 0gscan ops 开工单申请，字段与口径有疑问直接找 Chain 后端确认。
